# Draft upstream issue (not filed; owner decides, open question 9)

**Title:** Nondeterministic SMT output: `arrow_*` accessors are emitted in
`HashMap` order (enum_synthesize.rs)

**Body:**

Verifying the same input twice can send Z3 different bytes. With release
`0.2026.10.04.426d8b0`, `examples/syntax.rs` produced 2 distinct solver input
streams in 6 runs. The differences are in the order of the declarations and
fuel lists for the generated `arrow_*` accessor functions.

The cause appears to be `source/builtin_macros/src/enum_synthesize.rs`. At
line 92, `direct_fields` is a `std::collections::HashMap`; at line 155, the
`arrow_<field>` methods are generated by iterating over it. With
`RandomState`, the iteration order changes between processes.

**Impact:** the verdicts are the same, but anything that relies on
reproducible solver input sees spurious differences. That includes
query-level caching, comparing SMT logs between runs, and instability
studies. Z3's search can also depend on declaration order, so run-to-run
differences in proof effort are possible in principle.

**Suggested fix:** use an insertion-ordered map (for example `IndexMap`, or a
`Vec` plus a lookup map), or sort `direct_fields` before generating the
methods.

**Reproduction:** run `verus --crate-type=lib examples/syntax.rs` several
times with `VERUS_Z3_PATH` pointing at a wrapper that tees stdin, and compare
the captured streams.
