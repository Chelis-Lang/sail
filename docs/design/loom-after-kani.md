# Loom after Kani

Kani has no concurrency support: it warns and compiles concurrent code as sequential, and does not check data races. Loom is the obvious candidate for that gap. This record holds the analysis; the spike result is added here when it runs. Status: analysis record, 2026-11-27, part of [the Kani phase](kani-phase.md). No Loom work is scheduled.

**Recommendation: not the next backend. A cheap, spike-gated client of the Kani executor, after SAT and SMT solver work.**

- **What Loom is:** tests built with `--cfg loom` rerun a closure under every permitted thread schedule, bounded by preemptions, branches, permutations or duration. No solver; exploration is in-process test code.
- **The pain is real but narrow:** Tokio's loom suite hit GitHub's six-hour limit and now runs at two preemptions, split per module, only on labelled PRs. Crossbeam measured two hours at a bound of three against thirteen minutes at two. Confirmed users are a handful of infrastructure crates (Tokio, crossbeam-epoch, bytes, quinn, s2n-quic-core).
- **What Sail can add:** exact per-test receipts over the authenticated closure, Loom version and every `LOOM_*` setting, so unchanged suites never rerun; a signed CI tier; supervised budgets in place of label-gated jobs. It is a test-result cache: there is no engine boundary to shim, so nothing finer than a whole test can be reused.
- **What weakens the evidence claim:** one release in two years before 0.7.3 (2026-11-08); open issues where exploration is silently disabled, interleavings are possibly missed and a false positive is reported; checkpointing panicked on every model through 0.7.2, which blocks failing-schedule replay as a validated witness. A search cut off by a duration or permutation cap must be reported as no-claim, and whether Loom reports that cut-off reliably is unconfirmed.
- **What it reuses unchanged:** the cargo-shaped batch executor, input-closure authentication, receipts, the bounded-evidence types (new bound kinds: preemptions, branches, permutations), corpus and bench lanes, the fleet. Shuttle (AWS, randomized, weekly releases, replayable schedule strings) maps onto the existing `sampled` tier with the schedule as witness, and comes with it nearly free.
- **The strategic link is to D.I.V.E.:** D.I.V.E. already validates Rust-recorded traces against a TLA+ spec (`dive validate-trace`). Loom or Shuttle executions emitting per-schedule event logs, checked against a spec, would connect implementation and model. That depends on D.I.V.E.'s partial-trace work (dive #1282, #1299), so it is a D.I.V.E.-paced follow-up.
- **Other concurrency routes:** Miri's GenMC mode is bounded-exhaustive over the real memory model but experimental and needs a hand-built Miri; Verus concurrency (tokenized state machines) is already served by Sail's Verus path.
- **Deciding spike (two to three days, after Kani's L1 receipts exist):** run Tokio's `sync` and crossbeam-epoch loom suites through the Kani executor with per-test receipts over 20 recent commits. Go if receipts remove at least half of loom CI time, truncation is detectable, and checkpoint replay works on 0.7.3. If it passes, Loom and Shuttle go ahead of Creusot because the integration cost is small. If it fails, it closes with the record.
