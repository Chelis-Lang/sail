# Neutral contracts, version 1

Status: first implementation slice. This interface is independent of the existing
Verus input path. It does not establish a proof merely by compiling a contract.

## Source interface

The private `sail-contracts` crate exports `requires`, `ensures`, `requirement`
and `satisfies` attributes. They may appear in any order. A contracted function
has zero or more `#[requires(boolean_expression)]`, exactly one
`#[ensures(|result| boolean_expression)]`, and exactly one
`#[satisfies("REQ-ID")]`. A pure predicate uses
`#[requirement("REQ-ID")]`. IDs are nonempty strings of ASCII letters, digits,
underscore, period, slash, colon and hyphen, at most 256 bytes. They are owner
identities, never inferred from line numbers. The same ID may occur on its
predicate and its implementations. It may not name two predicate definitions.

Predicates have explicit Boolean return types, by-value scalar parameters and
a call-free pure expression body. Supported expressions are scalar literals,
parameter paths, field projections, parentheses, unary negation/not, binary
arithmetic/comparison/Boolean operations, and conditional/block expressions.
No assignments, mutable references, arbitrary method calls, macros, loops,
recursion, async, unsafe or external effects are admitted in predicates.
The generated predicate entry point is a checked scalar computation, not a
trusted purity annotation. A contract may call such a predicate, using its
ordinary qualified source path; expansion routes that call through the entry
point generated by the predicate attribute. Other calls are rejected. Whole
source admission rechecks resolution and the actual predicate body before any
verification; a symbol name alone is never evidence of purity.

The first runtime subset admits nongeneric free functions and inherent methods
over Boolean and fixed-width integer values. Shared and mutable receivers may
read and write scalar fields. Bodies use bindings, assignments, arithmetic,
comparisons, `if`, blocks and returns. Return values are owned and `Copy`:
scalars or `Copy` scalar structs. Ordinary executable function calls are not
admitted in this first slice; specification calls target checked predicates.
Trait methods,
generics, reference returns, opaque macros, unsafe, async and loops are rejected.
This is an explicit subset, not a claim that arbitrary Rust can be lowered.
Whole-source admission additionally resolves supported calls, rejects recursion
and checks types and source ownership; attribute expansion does not claim to
replace the Rust type checker or a whole-crate verifier.

## Evaluation and arithmetic

All preconditions run in source order before the body. A false condition stops
execution with a contract violation. Checks remain enabled in release builds.
The body runs once. Postconditions inspect its actual return value and final
state after every normal return, including an early `return`. Unwinding does
not produce a successful result or execute a normal-return postcondition.

`old(expression)` is valid only inside a postcondition. Each occurrence captures
its scalar value once after preconditions and before the body. The argument
may contain a parameter, scalar field projection or a pure scalar expression;
it cannot call code or retain a reference into mutable state. Whole-source
admission verifies the captured type is scalar. Runtime expansion uses an
explicit scalar trait bound to reject arbitrary `Clone` implementations.

Contract and predicate arithmetic uses checked operations, including in release
mode. Fixed-width values keep their signedness and width. A failing arithmetic
operation is a contract evaluation failure, never a true Boolean result.
Executable-body arithmetic retains Rust semantics; a verified backend must
prove absence of arithmetic faults under the preconditions before reporting
the function verified. No silent mathematical-integer substitution is allowed.

`Int` holds `i128` at runtime, with checked arithmetic that stops on overflow,
division by zero and invalid remainder. Verification interprets `Int` as a
mathematical integer. This approved distinction is an arithmetic qualifier of
the evidence, not a promise that all mathematical values are runtime representable.
Bounded and unbounded quantifier syntax is reserved for a later qualified
implementation. It is currently rejected explicitly; unbounded quantifiers
will be verification-only and must never become runtime checks.

## Shared representation and lowering boundary

`sail-contracts-ir` parses and validates the same attributes and expressions used
by the runtime macro crate. It exposes owned, versioned contract records,
requirement identities and original Rust syntax with source ranges. It performs
no filesystem access, solver execution, caching or verdict construction.
`sail-contracts-macros` uses it for expansion. `sail-contracts` contains the
small checked runtime and reexports the attributes. No runtime crate depends
on the verifier, daemon or API.

The later Verus adapter consumes an admitted source closure and returns an owned
shadow project and a mapping manifest. The manifest binds original source,
contracts, requirement predicates, supported arithmetic, lowering version,
generated files, generated symbols and source spans by content hash. Unsupported
syntax is an explicit error before dispatch. The original workspace is not
modified. Backend verdicts are mapped only from actual attributed obligations.
One guarantee per function in this slice prevents an aggregate function failure
from being falsely attributed to several distinct properties.

Oyster owns contract-to-requirement entailment. Sail supplies contract metadata
and executes the independent SMT request; it never infers a requirement's
meaning or treats matching requirement IDs as an entailment proof.

## Acceptance

The runtime tests cover precondition and postcondition violations, an early
return, body-once evaluation, independent old captures of mutable state,
non-scalar capture rejection, invalid syntax and purity rejection. Checked
arithmetic and `Int` overflow are tested in both test and release profiles.
The shared parser tests preserve deterministic source order and requirement IDs.
These tests establish runtime behavior only; SMT evidence requires the later
actual backend, source-to-shadow mapping and conformance acceptance.
